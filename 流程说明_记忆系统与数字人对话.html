二、记忆系统：一条闭环，五个环节

记忆不是"知识库"，而是"情绪病历本"。每轮对话结束写一条快照，下一轮开始前读最近 10 条，压缩成一段中文摘要塞进 Prompt，再用最近 3 条判断是否持续恶化来改写风险等级。

2.2 三个消费点

用途函数参数做什么

2.3 记忆怎么进入 Prompt

记忆不是独立的一条消息，而是与"本轮语音/表情标签"共用同一条 system message——这是当前实现的一个关键设计（也是后面要提的问题之一）。

system ①
树洞人设 + 四级风险定义 + 强制 JSON 输出格式（llm_provider.SYSTEM_PROMPT，硬编码）
system ②
「用户近期情绪趋势：【1】今天又被投诉了（情绪：愤怒焦虑，风险3级）; 【2】…；语音情绪：悲伤/sad(0.72)；表情情绪：sadness(0.81)」
← 前半段来自记忆，后半段来自本轮模态
user
本轮文本（语音输入时为 FunASR 转写结果）
注意：messages 里没有历史对话。模型只知道"最近 10 次的情绪梗概"，不知道"上一句具体说了什么"。这会让连续对话出现重复共情、追问已答过的问题。

2.4 记忆怎么改写风险等级

趋势提升规则（miniprogram.py:216）

if riskLevel >= 2 and 最近3条记忆的 risk_level 全部 <= 3:
    riskLevel = max(2, riskLevel - 1)  # 数值减 1 = 等级提升一级

为什么封底在 2 级：1 级危机只能由模型明确识别自杀意念、或"文本低风险 + 表情/语音极高痛苦"的矛盾提升触发。趋势提升不允许把用户直接判成 1 级，避免误报把用户推给急救资源。

6.2 与 PRD 口径不一致（必须统一说法）

维度PRD 写的代码实际 / 建议口径
记忆系统Mem0 + Chroma/FAISS 向量库，语义检索 SQLite 时序快照（最近 10 条）。口径：provider 已抽象，当前为关系型实现，向量库为阶段四替换项——不要讲成"语义检索已实现"
大模型EmoLLM 本地部署 deepseek-flash 云端 API。口径：云端通用模型过渡通道，EmoLLM 接入只改 provider
调试台判定链— _judgment_chain 的趋势提升没有 2 级封底（可能 3→2→1），与小程序链路不一致。建议抽成同一函数
digitalHumanAction驱动数字人动作 后端返回 emergency/worry/comfort/listen，但 H5 只用 intervention.type 决定 UI，该字段未被消费

6.3 可选增强

  • 记忆向量化：content 过 embedding 存 Chroma，检索改成"近 10 条 + 语义 top 3"，才对得上 Mem0 语义。
  • 记忆分层：会话级摘要（每 5 轮压缩）+ 用户级画像（职业 / 作息 / 高频触发场景），避免 10 条截断丢失长期信息。
  • 首字延迟优化：LLM 流式返回 + 数字人分段 speak，把"松手 → 开口"从 3~6s 压到 1.5s 内。
  • 模型预热：_preheat_models() 已在启动时跑，但 FunASR 首次推理仍慢，可加空音频预热。
